# Decisions

- **Write Settle Time**: 30s blocking period in [`coordinator.py`](/workspaces/xtherma_ha/custom_components/xtherma_fp/coordinator.py) (`_WRITE_SETTLE_TIME_S`) prevents stale device data from overwriting fresh writes.
- **Vendored Pymodbus**: Used to ensure stability / avoid dependency conflicts in the HA environment. *(Superseded by D4: the vendored copy under `custom_components/xtherma_fp/vendor/` is dead; deletion pending approval.)*
- **D1 (modbus transport base)**: `xtherma-modbus` MVP uses `pymodbus` as transport base (offline-buildable; vendored copy in the integration). Final target is `modbus-connection`. Transport is isolated in the library's `transport.py` so the swap is cheap. *(Superseded by D4.)*
- **D4 (modbus transport base v2 — `modbus-connection`)**: `xtherma-modbus` 0.2.0 builds on HA's official `modbus-connection` abstraction (`>=4.10.0,<5`, HA core pins `==4.10.0` with the tmodbus backend) instead of raw pymodbus. The library no longer owns a transport or lifecycle: consumers pass a pre-bound `modbus_connection.ModbusUnit` handle (in HA via `homeassistant.components.modbus.async_get_unit` / `async_get_temporary_unit`; standalone via `ModbusConnection(params).for_unit(id)`), so the unit id travels with the binding — `XthermaFP(unit)` takes no `address`. `transport.py` is deleted. Unit owners must never close or `disconnect()` the shared link; `async_connect`/`async_disconnect` are documented no-ops. Both backends map their native errors into the neutral `modbus_connection` hierarchy, translated once in `device.py::_translate` onto the stable contract: `ServerDeviceBusyError`→`XthermaModbusBusyError`, `ModbusConnectionError` (incl. `ClientClosedError`)→`XthermaNotConnectedError`, anything else→`XthermaModbusError`. Breaking: v0.2.0. Side effects: shared serialized link per `host:port` (conflicting link settings surface as `HomeAssistantError`); the per-client 2 s timeout is replaced by the shared connection's (HA default 10 s).
- **D2 (modbus data model)**: Path B — the library data model is pure Python, HA-free; HA rendering is resolved by `key` in the integration. *(Field list split by D5: semantics on `Quantity`, transport placement on bindings.)*
- **D3 (REST path)**: The REST client stays in the integration (aiohttp + HA rendering, not Modbus). The library quantity table is the single source of truth for *device semantics*; REST consumes bindings for `factor` scaling only (Modbus addresses irrelevant). HA rendering fields (device_class/state_class/icon/mode) move into a `key` → HA-description mapping in the integration (Phase 3), shared by both transports; entity discovery still flows through the `XthermaClient.get_entity_descriptions()` ABC. Transport key sets diverge (REST-only `error_1`/`error_2`; Modbus-only `808`/`815`/`x2400`/`x2401`). *(The "both live in the library table, with/without address" convention is superseded by D5: divergence is binding existence.)*
- **D5 (quantity/binding split)**: *What a value means* is separated from *where a transport reads/writes it*: `Quantity(key, name, unit, factor, options, min/max, signed)` is transport-neutral (`quantities.py`); `ModbusBinding(quantity, address, writable)` and `RestBinding(quantity, api_key)` carry the transport placement (`bindings.py`). Availability per transport is **binding existence**, not a `register: int | None` sentinel (supersedes the D3 with/without-address convention). `writable` is a Modbus binding property (REST is read-only); exactly **one shared `factor` per quantity** (no per-transport scaling). `api_key` (defaults to the quantity key) isolates entity/translation keys from Fernportal wire-key renames. The legacy combined `Register` record and its `REGISTERS`/`REGISTER_BY_KEY` facade are deleted. Authoring is neutral: quantities live in `quantities_settings.py` / `quantities_telemetry.py` (REST-only rows in `quantities.py`); `bindings.py` holds pure reference tables — `_MODBUS_ROWS` (`key, address, writable`) and `_REST_QUANTITY_KEYS` — resolved through `QUANTITY_BY_KEY`, so no transport module ever defines a `Quantity`.
- **D6 (library rename)**: The device library `xtherma-modbus` (import `xtherma_modbus`) is renamed **`pytherma`** (import `pytherma`, vendored at `custom_components/xtherma_fp/pytherma/`). The transport-specific name was misleading: the library always modeled device semantics for **both** transports (Modbus + Fernportal REST bindings) and, since D4, owns no Modbus transport itself. Package/import rename only — public symbols (`XthermaFP`, `Xtherma*` exceptions) and the `modbus-connection` dependency are unchanged. Historical references to `xtherma-modbus`/`xtherma_modbus` in D1/D4 (and in `CLEANUPS.md`/`PLAN-quantity-binding-split.md`) refer to `pytherma`.
- **D7 (REST `out_hp_kw` ignored)**: The Fernportal key `out_hp_kw` (kW, `output_factor: clamp(x/100,0,120)`) duplicates `out_hp` (W, factor ×10; same raw value ÷100 vs ×10) and is **deliberately not modeled**: no quantity, no REST binding — `out_hp` is sufficient. The REST client skips unbound keys silently, so no code is involved; the drift tool's recurring "served by the API but missing a quantity: out_hp_kw" finding is accepted noise, not an open item. Revisit only if the two ever diverge on the wire.
